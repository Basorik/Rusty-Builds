## 1. The Three Naming Systems

Every stat in Path of Exile exists in **three different representations**. Understanding these is critical — they are the source of most complexity in the data pipeline.

### 1a. Internal Stat IDs (GGG's names)

These are the identifiers GGG uses in their game data files. They appear in RePoE exports, the passive tree `stats` maps, gem data, and mod definitions.

**Format**: Snake-case with `+%`, `_per_`, and suffixes like `_while_on_low_life`.

**Examples**:
| Internal Stat ID | What it means |
|---|---|
| `base_strength` | Flat added strength |
| `attack_speed_+%` | % increased attack speed |
| `base_life_regeneration_rate_per_minute` | Flat life regen (per minute, needs /60) |
| `accuracy_rating_+%_when_on_low_life` | % increased accuracy, conditional on Low Life |
| `physical_damage_+%` | % increased physical damage |
| `base_critical_strike_multiplier_+` | Flat added crit multiplier |
| `additional_strength` | Flat added strength (alternate internal name) |

**Where they appear**:
- RePoE `passive_skill_trees/Default.json` → `passives[id].stats` keys
- RePoE `mods.json` → `stats[].id` field
- RePoE `gems.json` → `per_level[].stats` keys
- PoB `SkillStatMap.json` → top-level keys
- GGG tree `data.json` → NOT present (uses display text only)

### 1b. Display Text (Human-readable)

The text shown in-game and in the GGG tree JSON's `stats` arrays. Generated by GGG's stat description system by substituting values into templates.

**Format**: English sentences with numbers substituted in.

**Examples**:
| Display Text | Internal Stat ID | Value |
|---|---|---|
| `+10 to Strength` | `base_strength` | 10 |
| `5% increased Attack Speed` | `attack_speed_+%` | 5 |
| `+30% to Fire Resistance` | `base_fire_damage_resistance_%` | 30 |
| `Minions deal 10% increased Damage` | `minion_damage_+%` | 10 |

**Where they appear**:
- GGG tree JSON → `nodes[id].stats: ["display text 1", "display text 2"]`
- Item mod text shown in-game
- Tooltip rendering

**The stat_translations system** (RePoE `stat_translations.json`) defines how to convert internal stat IDs + values → display text. Each entry maps one or more internal stat IDs to a template string like `"{0}% increased Attack Speed"`.

### 1c. Calc Variable Names (PoB's engine names)

These are the names Path of Building's Lua calc engine uses internally. They are what our `StatId` enum variants map to.

**Format**: PascalCase, compact, omitting obvious context.

**Examples**:
| Calc Variable Name | Rust `StatId` | Internal Stat ID(s) |
|---|---|---|
| `Strength` | `StatId::Strength` | `base_strength`, `additional_strength` |
| `Speed` | `StatId::Speed` | `attack_speed_+%`, `cast_speed_+%`, `base_cast_speed_+%` |
| `Life` | `StatId::Life` | `base_maximum_life`, `maximum_life_+%` |
| `CritChance` | `StatId::CritChance` | `critical_strike_chance_+%`, `base_critical_strike_chance_+%` |
| `FireResist` | `StatId::FireResist` | `base_fire_damage_resistance_%` |
| `Accuracy` | `StatId::Accuracy` | `accuracy_rating`, `accuracy_rating_+%` |
| `Damage` | `StatId::Damage` | `damage_+%` (generic — flags narrow it to attack/spell/etc.) |

**Key insight**: Multiple internal stat IDs map to the same calc variable. `attack_speed_+%` and `cast_speed_+%` both map to `StatId::Speed` — the difference is captured by `ModFlag::ATTACK` vs `ModFlag::CAST`.

**Where they appear**:
- `SkillStatMap.json` → `name` field in each mapping entry
- `StatId` enum in `data/stat_id.rs` (346 variants)
- `ModDB` queries: `mod_db.sum_base(StatId::Strength, &ctx)`

### 1d. The Translation Chain

```
Internal Stat ID          Calc Variable Name         Display Text
"attack_speed_+%"   ──→   StatId::Speed         "5% increased Attack Speed"
                      ↑                              ↑
              SkillStatMap.json                stat_translations.json
              (+ ModType + Flags)              (template substitution)
```

The **critical bridge** is `SkillStatMap.json`: it maps ~707 internal stat IDs to calc variable names, modifier types, flag bits, and optional condition/multiplier tags. Without it, we'd have to parse display text (fragile, incomplete).

### 3b. Data Transformations During Load

#### PassiveTree (GGG tree JSON)

The tree JSON deserializes directly into Rust types with serde rename attributes:

```
JSON "skill" field  → PassiveNode.id: Option<u32>
JSON "in"/"out"     → PassiveNode.in_connections/out_connections: Vec<String>
JSON "grantedStrength" → PassiveNode.granted_strength: u32
JSON "ascendancyName" → PassiveNode.ascendancy_name: Option<String>
JSON "isKeystone"   → PassiveNode.is_keystone: bool
JSON "stats"        → PassiveNode.stats: Vec<String>  ← DISPLAY TEXT (the problem)
JSON "masteryEffects" → PassiveNode.mastery_effects: Vec<MasteryEffect>
JSON "classes"      → PassiveTree.classes: Vec<ClassData>
```

**Key issue**: The tree JSON only has display text stats (`"+10 to Strength"`), not internal stat IDs. This is why we need the RePoE `passive_skill_trees/Default.json` as a supplement — it provides the same nodes but with `stats: {"base_strength": 10}` format.

#### GemItem (PoB Gems.json)

Gems.json is a flat map of gem_id → gem metadata:

```
JSON key (e.g. "SummonRagingSpirit")  →  map key
JSON "name"              → GemItem.name
JSON "grantedEffectId"   → GemItem.granted_effect_id (links to Skills)
JSON "naturalMaxLevel"   → GemItem.natural_max_level
JSON "tags"              → GemItem.tags: FxHashMap<String, bool>
```

`GemItem` is metadata (name, attribute requirements, tags). The actual **mechanics** (per-level stats, skill types, support matching) live on `GrantedEffect` in `data/skills.rs`.

#### GrantedEffect (PoB Skills/*.json)

Each Skills file is a map of granted_effect_id → full skill/support data. Requires extensive custom deserialization because PoB's JSON uses both arrays and maps interchangeably:

- `skillTypes` → map `{"1": true}` OR sparse array `[null, true, null, true]` → `FxHashMap<u32, bool>`
- `levels` → array `[{...}]` OR map `{"1": {...}, "20": {...}}` → `Vec<GrantedEffectLevel>`
- `cost` → map `{"Mana": 9}` OR empty array `[]` → `Option<FxHashMap<String, f64>>`
- `qualityStats` → map `{"Default": [...]}` OR empty array `[]` → `QualityStats`
- `baseFlags` → map OR empty array → `FxHashMap<String, bool>`
- `statMap` → map OR empty array → `FxHashMap<String, Value>` (kept as raw Value)

Each `GrantedEffectLevel` has:
- `level_requirement`, `crit_chance`, `damage_effectiveness`, `mana_multiplier`, `cooldown`
- `stat_values: FxHashMap<String, Value>` — positional stat values with keys `"1"`, `"2"`, etc. corresponding to the parent `stats` array
- `stat_interpolation: Option<Vec<u32>>` — 1=static, 2=linear, 3=effectiveness scaling

#### SkillStatMapDB (PoB SkillStatMap.json)

The most complex loader due to **three JSON shapes** in the same file:

**Shape 1 — Array** (most entries):
```json
"attack_speed_+%": [{
    "flags": 1, "keywordFlags": 0,
    "name": "Speed", "type": "INC"
}]
```

**Shape 2 — Bare Object with numbered keys** (~72 entries):
```json
"some_stat": {
    "div": 100,
    "1": { "name": "SomeCalcVar", "type": "BASE", "flags": 0, "keywordFlags": 0 },
    "2": { "name": "OtherCalcVar", "type": "INC", "flags": 0, "keywordFlags": 0 }
}
```

**Shape 3 — Empty array** (~50 entries):
```json
"some_unused_stat": []
```

**Loading process** (`SkillStatMapDB::load()`):
1. Deserialize entire file as `FxHashMap<String, serde_json::Value>`
2. For each entry, normalize to `Vec<Value>`:
   - Array → use directly
   - Object → extract numbered keys `"1"`, `"2"`, `"3"`, inject parent's `div`/`value`
   - Other → skip
3. Deserialize each `Value` into `RawStatMapping` (with typed serde fields)
4. Convert `RawStatMapping` → `StatMapping` via `convert()`:
   - `name` → `StatId::from_name()` (O(1) FxHashMap lookup via OnceLock)
   - `type` → `parse_mod_type()` → `ModType` enum
   - `flags` → `ModFlag::from_bits_truncate()`
   - `keywordFlags` → `KeywordFlag::from_bits_truncate()`
   - `"1"`, `"2"` tags → `parse_raw_tag()` → `ModTag::Condition` or `ModTag::Multiplier`
5. Entries that fail any conversion step are silently dropped (logged)

**Coverage**: 599/707 internal stat IDs loaded. The 108 unresolvable entries are:
- Empty arrays `[]` (~50) — intentionally unmapped
- `skillFlag` entries — set flags on skills, not calc stats
- `PerStat` multipliers — complex per-stat scaling not yet modeled

## 5. The Modifier System

The modifier system is the heart of the calculation engine. Every stat bonus from any source (tree nodes, items, gems, config) becomes a `Modifier` stored in a `ModDB`.

### 5a. Core Types

```rust
// src-tauri/src/modifier/types.rs

/// The 8 modifier types, matching PoB's ModDB.
pub enum ModType {
    Base,       // Flat added value (e.g. +10 to Strength)
    Inc,        // % increased (additive with other increases)
    More,       // % more (multiplicative with everything)
    Flag,       // Boolean flag (e.g. "Cannot be Stunned")
    Override,   // Overrides the final value (highest priority)
    List,       // List-type modifier (complex, Phase 5+)
    Max,        // Caps the final value
    Min,        // Floors the final value
}
```

```rust
/// Conditional tags attached to modifiers.
pub enum ModTag {
    Condition(Box<str>),     // "LowLife", "UsingFlask", "Leeching", etc.
    Multiplier(Box<str>),    // "EnduranceCharge", "FrenzyCharge", etc.
    SkillType(u32),          // Numeric skill type ID
    SlotName(Box<str>),      // Equipment slot
}
```

**Important**: `ModTag` uses `Box<str>` (not `StatId`) because condition/multiplier variable names like `"LowLife"` or `"EnemyFrozen"` are NOT calc variable names — they're a separate namespace of boolean conditions evaluated by `CalcContext`.

```rust
/// A single modifier from any source.
pub struct Modifier {
    pub stat: StatId,                    // Which stat this modifies
    pub mod_type: ModType,               // How it modifies (Base/Inc/More/Flag/...)
    pub value: f64,                      // Numeric value (1.0 for flags)
    pub flags: ModFlag,                  // Attack/Spell/Melee scope
    pub keywords: KeywordFlag,           // Damage type scope
    pub source: SourceId,                // Where it came from (node ID, item, etc.)
    pub tags: SmallVec<[ModTag; 2]>,     // Conditions/multipliers (inline ≤2)
}
```

### 5b. ModDB — The Modifier Database

```rust
// src-tauri/src/modifier/mod_db.rs

pub struct ModDB {
    mods: FxHashMap<StatId, Vec<Modifier>>,    // StatId → all modifiers for that stat
}
```

**Query methods** (all accept `CalcContext` for condition filtering):

| Method | Signature | Formula | Use |
|---|---|---|---|
| `sum_base()` | `(StatId, &CalcContext) → f64` | Sum of all Base modifiers | Flat bonuses |
| `sum_inc()` | `(StatId, &CalcContext) → f64` | Sum of all Inc modifiers | % increased |
| `product_more()` | `(StatId, &CalcContext) → f64` | Product of `(1 + more/100)` | % more multipliers |
| `has_flag()` | `(StatId, &CalcContext) → bool` | Any Flag modifier exists? | Boolean keystones |
| `get_override()` | `(StatId, &CalcContext) → Option<f64>` | First Override value | Hard overrides |
| `get_max()` | `(StatId, &CalcContext) → Option<f64>` | Maximum of all Max mods | Stat caps |
| `get_min()` | `(StatId, &CalcContext) → Option<f64>` | Minimum of all Min mods | Stat floors |
| `calculate()` | `(StatId, &CalcContext) → f64` | Full formula below | Final value |
| `tabulate()` | `(Option<ModType>, StatId, &CalcContext) → Vec<(f64, &Modifier)>` | Filtered list | Debug/breakdown |

**The core calculation formula**:
```
calculate(stat) =
    if override exists → return override
    else → base × (1 + sum_inc/100) × product_more
```

## 6. Calculation Flow (End to End)

### 6a. Life Calculation (Current Implementation)

```rust
// In update_selected_nodes() — lib.rs

// 1. Get base from all layers
let life_base = 38.0                                    // Character base life
    + (build.level as f64 * 12.0)                       // 12 life per level
    + mod_db.sum_base(StatId::Life, &ctx);              // Tree + item flat life

// 2. Get increase % from all layers
let life_inc = mod_db.sum_inc(StatId::Life, &ctx);      // Sum of all "% increased"

// 3. Get more multipliers
let life_more = mod_db.product_more(StatId::Life, &ctx); // Product of all "% more"

// 4. Apply formula + STR bonus
let life = (life_base * (1.0 + life_inc / 100.0) * life_more).floor() as i64
    + (total_str / 2.0).floor() as i64;                 // +1 life per 2 STR
```

### 6b. General Stat Calculation Formula

```
final = override_check(stat) OR:
        base(stat) × (1 + sum_inc(stat)/100) × product_more(stat)
        then clamp: max(min_cap, min(max_cap, final))
```

Where:
- `base(stat)` = sum of all `ModType::Base` modifiers
- `sum_inc(stat)` = sum of all `ModType::Inc` modifiers (additive with each other)
- `product_more(stat)` = product of `(1 + mod.value/100)` for all `ModType::More` modifiers
- Override takes absolute precedence if present
- Max/Min cap the result after all multiplication

## 7. SkillStatMap: The Bridge

### 7a. What It Does

`SkillStatMap.json` is the **only source** that maps GGG's internal stat IDs to PoB's calc engine variable names. It defines the **semantic meaning** of each stat.

### 7b. Entry Anatomy

```json
"attack_speed_+%": [{
    "name": "Speed",           // → StatId::Speed (calc variable name)
    "type": "INC",             // → ModType::Inc
    "flags": 1,                // → ModFlag::ATTACK (bit 0)
    "keywordFlags": 0,         // → KeywordFlag::empty()
}]
```

This single entry tells us:
1. The stat `attack_speed_+%` affects the **Speed** calculation variable
2. It's an **increase** (additive % modifier)
3. It only applies to **attacks** (flag bit 0 = ATTACK)
4. It has no keyword restrictions

### 7c. One-to-Many Mappings

Some internal stats produce **multiple** modifiers:

```json
"active_skill_additive_minion_damage_modifiers_apply_to_all_damage_at_%_value": [
    {
        "name": "MinionDamageAppliesToPlayer",
        "type": "FLAG",
        "flags": 0,
        "keywordFlags": 0,
        "value": true
    },
    {
        "name": "ImprovedMinionDamageAppliesToPlayer",
        "type": "MAX"
    }
]
```

→ Produces 2 Modifiers: one Flag and one Max, from a single stat.

### 7d. Conditional Entries

```json
"accuracy_rating_+%_when_on_low_life": [{
    "name": "Accuracy",
    "type": "INC",
    "flags": 0,
    "keywordFlags": 0,
    "1": {
        "type": "Condition",
        "var": "LowLife"
    }
}]
```

→ Produces: `Modifier { stat: Accuracy, mod_type: Inc, tags: [Condition("LowLife")] }`

The condition tag means this modifier only applies when `CalcContext` says the character is on Low Life (≤35% max life).

### 7e. Division Entries

```json
"base_life_regeneration_rate_per_minute": {
    "div": 60,
    "1": { "name": "LifeRegen", "type": "BASE", "flags": 0, "keywordFlags": 0 }
}
```

→ The raw value is per-minute; dividing by 60 converts to per-second for the calc engine.

### 7f. Resolve Flow

```rust
skill_stat_map_db.resolve("attack_speed_+%", 5.0, SourceId(42069))
    │
    ├─ Look up "attack_speed_+%" in map → Vec<StatMapping>
    │     [{stat_id: Speed, mod_type: Inc, flags: ATTACK, keywords: empty, tags: [], div: None}]
    │
    ├─ For each StatMapping:
    │     final_value = div.map_or(5.0, |d| 5.0 / d) = 5.0
    │     → Modifier {
    │         stat: StatId::Speed,
    │         mod_type: ModType::Inc,
    │         value: 5.0,
    │         flags: ModFlag::ATTACK,
    │         keywords: KeywordFlag::empty(),
    │         source: SourceId(42069),
    │         tags: SmallVec::new(),
    │     }
    │
    └─ Return Vec<Modifier> [above modifier]
```
